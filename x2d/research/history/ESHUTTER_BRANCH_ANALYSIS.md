# X2D 100C：电子快门普通闪光同步分支分析

2026-09-09。本次目标是让电子快门在需要时、满足正常条件时可触发普通闪光；用户会选择合理的较慢曝光，不研究 HSS。本报告只分析官方第一代 X2D 100C 固件 4.2.0，不能当作当前实机固件或实际曝光轨迹。没有修改固件、生成补丁或向相机发送请求。

**结论：已有软件调用可达性的依据，但不能据此确认“只让一处不清零”就能达到目标。** 该位置复用了同步模式寄存器，另有镜头相关分支会在别处清零；实际闪光资格条件、热靴分路及共同曝光窗口尚未闭环。

**证据与复现。** 分析对象为 `.research-cache/system-librcam.so`，SHA-256 `72ebc8deebce4a29047c475e77ab4edbf2860abb1f572fea45260fe17ad0bda5`。固件来源及校验见 [firmware-manifest.json](../../../research/firmware-manifest.json) 和 [binary-manifest.json](../../../research/binary-manifest.json)。地址均为该 ELF 的虚拟地址。

- [Camx_StartExpo 原始反汇编](../../../research/x2d-4.2.0-Camx_StartExpo.asm.txt)：`0xa3b90`，3328 字节。
- [Camx_FlashEnable / Fsync / Xsync 原始反汇编](../../../research/x2d-4.2.0-Fsync-Xsync.asm.txt)。
- [字段初始化、断言及模式跳表摘录](../../../research/x2d-4.2.0-eshutter-context.asm.txt)。
- [trace_eshutter.py](../../../tools/trace_eshutter.py)：`py -3.11 tools/trace_eshutter.py` 只读固定 ELF，校验 14 条关键指令、6 个明确证据字符串及 4 项跳表，重新生成上述文本与 [校验清单](../../../research/eshutter-evidence-checks.json)。没有执行固件或模拟相机硬件。

**字段已知程度。** 下表的 `Expo` 是 `Camx_StartExpo` 保存到 `x19` 的首参数。未知字段使用偏移，不擅自命名为“灯已连接”“允许闪光”或某项安全检查。

| 简写 | 位置 | 本次静态证据 |
|---|---|---|
| E | `Expo+0x69` | `UserEShutter`。`0xa3d4c..0xa3d6c` 对应明确断言字符串；前置函数 `0xa2768..0xa278c` 将用户快门模式与 1 比较后写入此字节。 |
| S | `Expo+0x1ac` | `Camx_Init` 将其置 -1；`Camx_SetSensorMode` 保存第二参数，退出相关模式时恢复 -1。完整字段名和所有调用者仍未确认，不能解释为闪光灯检测。 |

| B | `Expo+0x61` | 前置镜头路径在 `0xa28d0` 将其清零；此轮未确认完整语义。 |
| L | `Expo+0x62` | `LensLongExposure`，有 `0xa27bc..0xa27d8` 的对应断言支持；它选择后文两个同步调用分支。 |
| G | 全局字节 `0x315d14` | `0xa42b4..0xa42c4` 读取并选择另一条路径。此轮未绑定字段名或实机默认值，不把它叫作普通用户选项。 |

**为什么“不清零”不等于保留已算好的布尔许可。**

`0xa4244` 先将 `w25` 置为模式值 3；其他前驱可设置模式 2 或读取 `Expo+0x63`。`S == -1` 时，`0xa42a8` 将 `w25` 作为参数传给 `Camx_FlashEnable`，继而进入 `FsyncCtrl_SetupAndEnable`。后者确实按 0～3 分派：跳表 `0x209a4c` 的模式 3 指向 `0xa7560`，在对应分路标志和 GPIO 对象存在时请求将相关 GPIO 置 1；它不执行模式 0/1/2 的镜头配置虚调用。该 GPIO 的物理作用不能仅从数值 1 推定。

随后，`w25` 才被复用为后续软件同步调用的零/非零条件。将这一段简化为稳定字段下的局部数据流，得到：

| 到达条件 | 原厂对 `w25` 的处理 | 假设只取消 `0xa43ac` 的赋零 |
|---|---|---|
| `G != 0` | `0xa42c4` 置 1 | 不经过目标清零点，保持原路径。 |
| `G == 0` 且 `A != 0 && B == 0` | 转到 `0xa43f4`，另一处赋零 | 仍为零；目标位置根本未执行。 |
| `G == 0`，不满足上一行，且 `E != 0` | `0xa43ac` 赋零 | 保留先前模式值；在本段 E 保持非零的前提下，前驱为模式 3，后续非零判断会通过。 |
| `G == 0`，不满足镜头分支，且 `E == 0` | `0xa43d0..0xa43d8` 重新计算 `w25 = (S == -1)` | 此路径不变。 |

因此，这个局部假设不会让所有曝光都调用软件同步，但也不能描述成“原有资格条件完整保留”。它保留的是模式数值，且无法覆盖另一处清零路径。究竟哪个路径覆盖用户镜头，仍需将镜头接口类型、A/B 字段和上游快门选择完整对应起来。

`S == -1` 也不应被随意当成闪光许可。值得保留的前置证据是：`Camx_PreStartExpo` 在 `S != -1` 的分支检查用户快门模式，并有 `user_shutter_mode != DCAM_USER_SHUTTER_MODE_ELECTRONIC` 断言（`0xa2800..0xa2824`）。所以仅在局部表中组合出 `E != 0, S != -1`，不能证明正常实机能到达这个组合。完整资格结论还必须考虑这些前置不变量及断言的运行语义。

**保留条件之后能到哪里。**

两个后续调用点分别是 `0xa44d8` 和 `0xa455c`，目标均为 `FsyncCtrl_TriggerXsync` (`0xa76b8`)。`0xa44d0`、`0xa4554` 以及回汇边 `0xa4790`、`0xa484c` 测试 `w25`。L 及其他镜头路径决定经过哪一个调用点；它们是同一函数中不同分支的调用位置，不能据此声称每次曝光会产生两次同步。

`FsyncCtrl_TriggerXsync` 再依据其对象 `+0x18` 选择直接热靴或镜头接口路径。直接路径顺序为：

1. `0xa76d0`：调用 `lenc_hotshoe_set_xsync(1)`；
2. `0xa76d8`：调用 `DjiSys_USleep(1000)`；
3. `0xa76e0`：调用 `lenc_hotshoe_set_xsync(0)`。

该片段没有反馈读取，顺序符合请求维持同步信号后撤销的结构；1000 是代码中等待函数的参数，不是等待引闪器反馈、无线提前量或闪光发光持续时间。GPIO/热靴物理极性、实际脉宽精度与运行时选中的分路尚未实测。即使未接外部闪光灯，额外进入这一分支也会执行调用及等待，不能当作对曝光时序毫无影响。

**尚缺什么。** 当前能证明局部软件路径的存在，尚不能证明按正常条件启用电子快门普通同步的完整行为。主要缺口是：A/B/G 及 S 的完整语义与有效状态组合、普通闪光设置和设备能力如何进入这条链、对应运行分路的初始化及下游行为、传感器各行共同曝光窗口与同步调用发生时刻的关系。较慢曝光可能为共同窗口提供条件，但不能靠本段代码给出可靠的具体快门阈值；早先约 1/4 秒的设想没有升级为测量结果。

本报告的可交付结论是：**存在可继续核查的软件切入点；“只不清除这一处”尚不是已证实的完整方案。** 当前没有实机验证、固件修改或补丁产物，也未研究 HSS。
