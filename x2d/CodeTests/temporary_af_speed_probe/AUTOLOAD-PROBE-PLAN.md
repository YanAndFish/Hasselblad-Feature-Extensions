# 独立预览进程启动验证候选

状态更新：独立进程动态加载已实机通过，诊断库随后删除，系统恢复只读；init 配置未安装，开机加载未验证。第一代 X2D 4.2.0；不是完整开机加载器。以下原始设计中图片测试宿主已被无界面的 camera-test --version 诊断宿主替代。

## 为什么选择此候选

原厂 `camera-gui` 的文件标签已有 init 到 GUI 域的转换。单独创建一个服务，使用该原厂可执行文件的图片测试参数，理论上可以在正确域启动独立进程。服务环境只为该进程指定一个自写诊断模块，既不停止主 GUI，也不全局设置预加载环境。

固定原厂策略允许 GUI 域读取、映射并执行 system_file 类型的库；su 域允许创建该类文件及向其目录添加条目。因此新库拟放在 `/system/lib64/libx2d_preview_probe.so`，不能直接假定 `/blackbox` 的数据文件标签同样允许装载。分区可写、动态链接器的实际装载和启动完整性仍未验证。

## 已有候选文件

- `autoload_probe.c` 与 `libx2d_preview_probe.so`：ARM64 PIC 共享模块，只使用原厂 libc 已有的八个导出函数，显式 DT_NEEDED libc.so，无文本重定位、无可写可执行段。用从同版固件读取的 libc 链接，避免把未声明运行库依赖的候选当作完整构建。
- 当前模块核对明确启用标记、原厂 camera-test 路径及 --version 参数；对普通主 GUI 和原测试服务命令行直接返回，不操作主 GUI。
- 仅在指定诊断进程中，独占创建 `/tmp/x2d-autoload-probe/status`，记录 root 与否、AT_SECURE 及自身 SELinux 域，随后退出，避免进入正常 GUI 主循环。它不会启动镜头、读照片、改按键、修改进程代码或调整策略。
- `x2d-preview-probe.rc.candidate`：独立服务配置草案，使用 camera-test --version，disabled + oneshot，**不会自动随开机运行**。用于后续区分 init 启动验证与正式自启动。原厂 `camera-gui` 服务不改。
- `check_autoload_probe.py`：九组编译后 ARM64 模拟通过，包括未启用、主界面、其他预览、错误程序、截断命令行、正常记录、状态文件已存在、上下文读取失败、短写失败。模拟 libc 不能证明真实相机装载。

## 下一批最小实机验证（尚未执行）

当前授权批次只涵盖调试接口及只读核对，不把它扩大为系统文件写入。

1. 保存当前 GUI、常驻预览身份和分区只读状态；对新库目标路径做不存在检查，拒绝覆盖已有文件。
2. 如获得明确系统写入授权，临时将实际活动 system 挂载改为可写，只创建诊断库，核对文件哈希、标签，立即恢复只读。错误时停止后续启动；报告实际清理结果，不假定已经恢复。
3. 经当前已验证的 GUI 域维护通道启动**独立诊断进程**，启用仅该进程的模块环境，读取标记。不得把该环境应用到原厂主 GUI，不使用全局加载器配置。
4. 这一步通过只证明模块在独立进程能加载。随后才考虑安装独立 init 配置、完整关机启动后的服务验证；配置本身读取时机及启动校验需另证实，不能以步骤 3 代替。
5. 诊断结束仅删除本批新增库及诊断临时目录，恢复原挂载状态，回读原厂 GUI 哈希与进程身份。失败时保留足够的状态说明，不重复启动未知状态进程。

## 正式开机加载仍缺

机内完成动态定位与初始化、输入设备身份发现、启动就绪检查、幂等行为、用户禁用标记、异常清理和完整卸载。现有电脑端脚本不能原样放入开机目录。系统存在双份分区，固件升级与切换分区时必须禁用未匹配版本的模块。

## 实机结果与边界

用户明确批准诊断库写入和独立加载测试。

首份图片测试宿主候选未留下模块标记，独立 GUI 运行到页面显示；用户观察到本地图片地址。该进程随后退出，诊断库被删除并恢复只读。不能将这一轮表述为加载成功，也不能仅凭输出确定其失败原因。

随后改用 camera-test --version 作为无窗口宿主，并显式链接原厂 libc。静态确认该程序在命令行处理之后才初始化总线和 TestdObject；版本选项在此之前处理。九组构造函数模拟通过。

修订版 SHA-256：`8735037ab1fa050f27e155acf9eee85719d31588e72d82815b824a9e62ba9106`。通过 su 调试会话新建诊断库，读回 hash 匹配、文件标签 system_file；立即恢复只读。随后从原维护通道运行独立版本查询进程，得到：

```text
module_loaded=1
uid=root
secure=0
domain=u:r:hbl_camera_service:s0
PROCESS_EXIT=0
```

该进程输出日志为空，原厂 GUI 与常驻预览 PID 仍为此前的两个实例；原 camera-test 服务仍在。随后按修订版哈希校验删除诊断库，挂载恢复为原始 ro 参数。

**这次宿主继承的是现有维护通道的域，不是由 init 新服务启动。** 结果证明该域能动态加载新 system_file 库；尚未证明 init 读取新配置、实际域转换、开机就绪及持久修改的启动完整性。未安装任何 init 配置，没有启动完整开机加载器。

收尾已回读：系统诊断库不存在；本批创建的 `/tmp/x2d-autoload-probe` 与 `/blackbox/x2d-autoload-probe`（含首轮图片宿主生成的本批缓存）已清理；ADB 自动关闭并恢复原 USB 组合；system 为 ro；主 GUI 与现有常驻预览仍为原实例，resident 状态 READY，原厂 GUI 文件 SHA-256 匹配基线。

## 用户重启后的实际结果：开机诊断通过

用户报告完整重启完成后，仅经维护通道读取，未手动启动诊断进程。设备 uptime 约 20 秒，主 GUI PID 为 363，与重启前不同。临时目录标记返回：

```text
module_loaded=1
uid=root
secure=0

```

`init.svc.x2d-preview-probe=stopped`；camera-gui、camera-service 均 running。新服务配置和库哈希均匹配安装值，原厂 camera-gui 哈希匹配基线。system_2 仍以原 ro 参数挂载；adbd stopped，USB 为原始 rndis,mass_storage,bulk,acm 组合。

这一结果验证了本次活动分区上新 init 配置在重启时被读取，独立服务可通过原厂入口在预期域加载诊断库。没有取得独立的 init 退出码日志，不将 stopped 单独当作退出码为零的证据。标记内容完整，源码对应流程在完成记录后退出。
