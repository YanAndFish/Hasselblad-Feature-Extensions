# 原厂主菜单接入核对

本轮仅离线读取附件与固定官方固件；没有执行附件、连接相机或更改开机配置。对方 AF-C 连续跟焦可用属于用户转述的实测结果，本报告不否定该结果，也不把它标成本站实测。

## 来源

- 用户附件 `x2d_afc_preload_usb(1).py`：2026-09 微信接收文件；核心修改库与编译 QML 副本未随附件提供，同目录检查不存在。
- 第一代 X2D 100C 官方 4.2.0，`camera-gui` SHA-256：`16391452abdc69de9e0807e065c0f4ab3f1ccb5fc288f6fc4e6f5cb3bdca12e0`。本轮提取时重新验证此哈希。
- 离线工具 `inspect_menu_resources.py` 和 `firmware_image.py`，读取本地系统镜像，无设备访问。

## 已核对的结构

附件第 37 行固定系统分区 p16；不能沿用到此前回读为 p17 的本机。附件第 109–124 行会停止原厂 GUI、按进程名等待退出，再用独立库启动原厂程序。这与现有两个同名 GUI 进程的独立常驻方案存在冲突，不能原样运行。

附件第 864–946 行验证加载标记、AF-C 门控、编译菜单副本及运行域，结尾仍提示手动检查 AF-C 可选。第 1454 行起组合调试界面启动与菜单补丁；第 1583 行起的单独 Debug Mode 属性设置不等同于此组合路径。附件不能独立交付，实际修改位于缺失的库中。

固件符号确认如下（均为 ELF 虚拟地址，不是当前进程绝对地址，也不是可直接写入的补丁）：

| 编译单元 | unit 结构地址 | 原始 qmlData 指针 | 第二字段值 |
|---|---:|---:|---:|
| ControlScreenViewModel.qml | 0x20ac690 | 0x16c6300 | 0x215cc90 |
| MainMenu.qml | 0x20acc60 | 0x17b2d10 | 0x216d440 |
| MainScreen.qml | 0x20acc78 | 0x17b67f0 | 0x216d650 |

这些 24 字节结构的第三字段当前均为零。附件定位的目标确实对应 ControlScreenViewModel；MainScreen 与 MainMenu 也有同类编译单元。结构存在不证明可任意替换，第二字段的函数表与新单元兼容性、引用生命周期及初始化时序仍须核对。

## 原厂图标、点击与返回

从固件资源读取的 `:/app/qml/mainmenu/MainScreen.qml`：

- 网格为三行，非稀疏模式四列；数据来自 `viewModel.favoriteModel`。
- 图标、标签、是否可点、菜单名称均由模型提供；不能只画第十二个图标就认为已接入原厂菜单。
- 点击经 `loadSubMenuItem` 进入 MainMenu 的路由。

`:/app/qml/mainmenu/MainMenu.qml`：

- 第 54–82 行检查媒体处理状态，再由 `SubMenu.menuFile(menuName)` 解析子页面，设置参数并交给 HblLoader。
- 第 146–171 行的加载器处理焦点和退出按键；不能只替换绘图部分而绕开这层交互。
- 第 99–112 行先关闭嵌套菜单，再清理模型和子菜单状态。
- 第 208–220 行进入子菜单时启用加载器和焦点；退回时将 source 清空。因此原厂此路由本身不满足用户要求的“引闪页面实例始终保留”。

## 候选设计及边界

1. 在原厂主菜单中新增“引闪”入口。先核对 FavoriteModel 与顶层菜单定义的扩展方式，或在 MainScreen 内实现明确独立的第十二格；不能虚构一个原厂不存在的菜单名称后直接调用 SubMenu。
2. 接入同一原厂主菜单页面树的独立引闪 UI 容器，保留原厂十一项路由与状态。引闪页面只展示 UI，不连接射频、功率、镜头或快门控制。
3. 为自定义容器单独定义显隐和返回，保留实例；既要消费自己的输入，也要跟随原厂退出菜单/半按回取景。不能把所有 closeMenu 调用都强制改回主菜单。
4. 在页面对象创建前完成兼容的编译单元/资源接入，核对函数表、类型与 Qt 版本。现有独立进程的开机入口只能作为启动阶段参考，不能因此假定可修改原厂进程的启动环境。
5. 原厂集成候选通过本地加载、往返、输入与实例生命周期检查后，再考虑设备适配。当前稳定独立菜单和开机配置本轮保持原样。

## 尚缺

- `libx2d_afc_gate.so` 及最好提供其源码/构建脚本。
- `x2d_controlscreen_afc_unit.bin`；完整复现另需两份 collector 和 probe 库。
- 对方实际运行记录，可区分构造成功、菜单显示与 AF-C 后端执行。
- 主菜单扩展及保留子页面实例的候选实现和验证。

结论：已经找到与对方方案对应的原厂主菜单结构和路由，可继续开展离线接入设计；尚未生成或安装原厂菜单补丁，不声称已经具备可部署版本。

## 续查：模型接口与页面常驻候选

进一步读取固定固件的符号、元对象表与反汇编：

- `FavoriteModel::init`（0x1050a20）从顶层菜单表构建项目，按可用性与可写条件处理，每条顶层记录为 32 字节。
- 内部存在 `FavoriteModel::addItem`（0x1050ba8），但该类自身的 Qt 元调用入口只分派 `onImageFormatChanged`、`reloadModel`、`count`、`itemEnabled`；没有直接暴露 `addItem` 给 QML。不能按普通 QML ListModel 的 append 用法修改这个 C++ 模型。
- `MenuX2d::menuFile`（0x358ca0）查找菜单名对应记录；找不到时返回空字符串。因此插入可视图标后仍要解决页面路由，不能假定自定义名字被接受。
- `HblLoader.qml` 第 38–49 行同时监听 source 和 active。任一更新使加载条件不满足时，内部 Loader 的 source 被清空。仅维持外层 QML 文件存在，不能保持子页面对象。

已新增 `original-menu-candidate/ResidentFlashHost.qml`，是尚未接入原厂进程的候选容器，直接实例化现有纯 UI 引闪页；用显隐控制保留实例，不依赖原厂 HblLoader 的销毁流程。它需要适配层提供菜单是否激活、是否正在处理媒体、是否已有原厂子菜单三个状态；没有相机或射频操作。

`original-menu-candidate/check_resident_flash_host.py` 用现有桌面 Qt 运行实际 QML（Python 3.11）：

- 默认创建隐藏，不在菜单状态或媒体忙/原厂子菜单打开时拒绝打开。
- 实际 Escape 按键先退详情，再退引闪页。
- 100 次进入和返回，底层 C++ 页面指针保持一致，未触发销毁，本地草稿保留。
- 退出主菜单或切到原厂子菜单会隐藏引闪页；重新进菜单不自动弹回。
- 运行 PASS，无 QML 警告，设备访问为零。

首次误用系统默认 Python 3.14 时，既有 PySide6 扩展在导入阶段异常退出；已明确限制验证脚本使用 Python 3.11。其后修正了 PySide 对 QML 自定义别名指针的转换方式，最终通过。没有相机进程受到影响。

该验证不覆盖原厂 KeyFn、真实主菜单模型注入、设备合成显示、实际开机耗时或 AF-C 后端；尚不能部署到相机。下一关仍是原厂页面的编译单元兼容接入，以及把原厂状态接到此容器，不能将桌面模拟的状态输入说成实机路由已通。
