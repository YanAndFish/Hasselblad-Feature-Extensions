# 错误 1000 与错误页日志导出

日期：2026-09-09；观察更新于 2026-09-10。静态输入仅为第一代 X1D-50c 官方 **1.25.0**，不是当前机身运行版本的确认。补充输入及哈希见 [error-input-manifest.json](error-input-manifest.json)，25 条调用与 9 项非敏感字符串复核见 [error-save-logs-static.json](validation/error-save-logs-static.json)，入口为 [audit_error_logs.py](../tools/audit_error_logs.py)。没有执行固件、导出日志或向相机发送命令。

用户已报告：重装电池后可操作菜单约 5–6 秒，随后出现错误 1000；多次重装不能消除；错误页下任何按键都没有效果，只有关机键有效。日志尝试的描述先是“没看有什么反应”，之后回忆短暂闪动，最新明确看见了“不要取出存储卡”，但所查看的卡上仍没有日志文件。以最新观察为准，不能继续写成“从未出现任何提示”，也没有确认持续转圈或执行完成。这些是用户观察，不是已取得的机内日志。**本说明不要求重复取电池或再次点击导出。**

## 错误 1000 能说明什么

`libappscommon` 的 `Errors::ErrorCodes` 明确将 `ErrorGeneral` 与 `ErrorFirstNonAckable` 都设为 1000；升级失败另有 1001，校准无效 1002、传感器板无效 1003、FARM 状态异常 1005、UART 内部问题 3000。1000 不是某个控制器或固件损坏的专码。

`system-manager` 的 `SystemManager::failEnter` 经 Qt 分发 `0x38494 → 0x1f5c4` 到达；普通失败分支在 `0x1f668` 设置 1000，`0x1f684` 调用 `CError::reportLocal`。特殊升级准备/测试状态另有分支。错误接收处理 `0x1e84c` 在没有优先保留的非可确认错误时设置当前错误，`0x1eaf8` 调用 `setCurrentError`，`0x1eb0c` 发 `systemFault`。GUI 的 `TouchWindow.qml:1668–1687` 隐藏正常主画面并显示 `PopoverError.qml`。

因此可确认“系统状态机进入失败可产生 1000”，不能只据 1000 或菜单停留时间确定最初失败者、哪次写入中断或哪个控制器需要重写。用户可先看到菜单也不能证明后台初始化已经全部完成。

## 错误页按钮的实际路径

`PopoverError.qml:171–185` 的 `saveLogsButton` 直接调用 `System.collectLogs()`；同一个点击处理器同步设定忙框文案“Saving log / Do not remove card!”，但显示状态绑定到 `System.collecting_logs !== 0`，并非点击就无条件显示。`subDialog`（225–240 行）初始 `active: false`、`visible: active`、异步加载。它与节点重试处理器独立。

调用经过 GUI 的 Qt 分发 `0x8e858 → 0x5a500 → 0x25af4`、`SystemManagerProxy::collectLogs`（`libappscommon:0x4ad60954`），发送 D-Bus 方法 `collectLogs`。服务端 `0x37354 → 0x1b6fc → 0x215c4` 调用 `Log::collect`（`0x32b94`）。

后端先检查是否已有未完成的日志请求；这里没有“错误 1000 / StateFail 时禁止”的额外判断。随后向 Storage 的 `Properties.GetAll` 查询卷信息。**允许执行不等于故障状态下能完成**：D-Bus、Storage、FARM 的卡访问及临时存储仍必须可用。

## 保存在哪里、需要什么

- 后端使用 Storage 的 `current_volume_image_raw`，从 `volumes` 中选择对应卷；值 0 对应文件卷类型 4，值 1 对应类型 5。它跟随当前 RAW 保存目标，没有在此处改保存卡，也不是任取一张插着的卡。没有匹配卷就报错。
- 文件名为 **`yyyyMMdd-hhmmsszzz-log.hbl`**，使用机身当时的日期时间，保存在该卷根目录。不能要求日期必须与电脑相同，也不应只搜索 `.zip` 或 `DCIM`。
- 先在 Linux `/tmp` 生成 `/tmp/logs.zip`，再调用 Storage 的 **`WriteFile(本地绝对路径, 文件大小, 目标路径)`** 送到卡；不是要求 SD 卡必须在 Linux 下挂成某个路径。
- 当前目标卡必须被 Storage 识别且可写；临时存储与卡均需要足够空间。所查入口和脚本没有一个固定的最小空闲容量检查；文件大小随历史日志变化，不能给出已验证的“留多少 MB 一定够”。只知道 Windows 能读取这张卡，不足以证明相机 Storage/FARM 当前能写它。
- 格式是密码保护的 ZIP 包装，内含 `hbl-logs.zip`，外层末尾补零至 512 字节整数倍，扩展名为 `.hbl`。它不是可安装固件。没有在研究产物中保存口令材料，也没有验证正式日志解读工具已经可用。

## 收集内容与副作用

已完整检查包内 `hbl-collect-logs.sh`（SHA-256 `c83dd12fd47a78f24e48f35560ca0b83a8f470fd867747cbe9585b3d3792e2d0`）：

- 收集 journal、build 信息、既有升级和错误记录、configstore 数据库。
- 对 13 个机内服务接口调用 `Properties.GetAll`，另读 `systemctl status --all`。
- 写临时文件、生成日志包、经存储服务写卡，然后清理自身临时目录。

所查日志处理链和完整脚本没有调用固件升级/节点重试/重启/拍摄/对焦。**它仍包含机内状态查询及通过 FARM 的卡写入**，不是纯读取操作；未逐个穷举所有属性 getter 的内部副作用，不能扩大为“完全不触碰控制器”。

严重错误另有 `hbl-save-error-logs.sh` 自动保存当前启动日志到 `/media/data/logs/error/<时间>/logs.zip` 的路径。它位于机内数据区，卡根目录没有 `.hbl` 不能证明这些机内记录不存在。本任务没有读取机内记录，也没有已确认可用的电脑端入口取得它。

日志可能含设备标识、配置、文件名或照片相关元数据。若将来取得指定导出文件，只读检查该文件并脱敏，不能将完整包、私有标识或照片信息收入研究仓库。

## 导出失败能否进一步分辨

`Log` 有以下独立失败分支；数值为内部日志结果码，**不是机身屏幕的错误 1000 编号**：

| 内部结果 | 静态失败条件 |
|---|---|
| 1 | Storage 属性查询的 D-Bus 回复失败 |
| 2 | 最终 Storage `WriteFile` 的 D-Bus 回复失败 |
| 3 | 预期临时日志文件不存在，或转存参数无效 |
| 4 | 收集进程启动/运行错误、非零退出或异常退出 |
| 5 | 所需卷/RAW 目标属性缺失，或没有匹配的目标卷 |

成功回复包含 `errorCode=0` 和 `fileName`；失败回复包含 `errorCode`。两者都会把 `collecting_logs` 清零。**错误页只把忙框绑定到这个布尔值，没有处理返回结果码；忙框消失不能单独证明写卡成功，也不能从它区分上述失败。** 收集脚本没有 `set -e`，部分子命令失败也不一定使最终退出码非零；即使以后存在一个包，仍需核查其中必需记录是否齐全。

最新“不要取出存储卡”与这条忙框文案相符，说明用户看见过等待提示。在固定 1.25.0 代码中，文案由点击处理器设置，而激活状态受 GUI 侧 `collecting_logs` 属性驱动；该属性对应机内服务状态。**这不是独立的脚本启动、打包进度或写卡确认**：未取得当前机身代码一致性、事件和 D-Bus 记录，也不能从旧/延迟属性值确认它属于哪个请求。成功与快速失败都会清掉忙框；没有 RAW 目标卷发生在 Storage 属性回复处理阶段，不是按钮点击前的 UI 拦截。

## 按键没有效果的解释范围

`TouchWindow.qml:152–153` 对非可确认错误选择 `error`，优先于普通升级/关机界面选择；1668–1687 行隐藏主画面、聚焦错误弹窗。继承的 `none_camera_view_menu` 会收掉相机视图、关闭其弹窗、停止滚轮高亮定时，并按 Wedge 焦点条件通知 BodySync 菜单状态。这足以说明普通操作界面被限制。

但 `PopoverError` 没有把保存按钮默认禁用，也没有映射全部物理按键；其按钮是触摸 `MouseArea` 路线。`IdleDetect.FilterNone=0` 也不能解释为“吞掉所有事件”：配置 setter 在 `victory-gui:0x652b8` 存入 `this+0x1c`，过滤器在 `0x65db4–0x65dbc` 发现零值后转 `0x65e18`，`0x65e24` 调用继承的 `QObject::eventFilter`，并非直接返回已消费。其他事件分支、焦点与后台状态仍可能影响运行结果，本轮没有全机事件追踪。

因此“普通按键不可用”与错误页设计相容，但“所有操作无反应”不能仅凭这段设计完整解释；也不能据此认定 Linux 全部停滞、某控制器损坏或机身已无法恢复。最新短暂等待提示更不支持把整个 UI 一概写成完全没有响应。

当前“点击过但没文件”尚不能区分目标卡不符、Storage/FARM 不可用、脚本/空间失败或写卡失败。没有日志包、返回码或当前机内记录时，继续猜具体坏件没有依据。

若用户之后明确提供某个卡盘符/指定导出路径，可仅在该卷根目录匹配 `*-log.hbl`，或只读指定文件；不搜索其他目录、不读取照片。找到包后先检查容器与完整性，保护层需使用已授权的正式读取方法，不能预先承诺内容已可解析。当前用户已尝试而没有导出成功，本轮不再安排同一步骤；恢复入口调查另行继续。
