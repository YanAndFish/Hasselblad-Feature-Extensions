# 传感器参数发送：软件缓存、SPC 回复与物理生效

2026-09-11，北京时间。本项是离线研究，没有新增设备请求、SPC 改写、拍摄或试闪。GFP3 已采样并解除，实机状态见 [记录说明](FARM_SENSOR_CAPTURE_V3.md)。

**SPI 请求的正常返回在底层发送路径之后，但成功回复仍不足以证明传感器参数锁存，更不能作为积分开始信号。** 已用原厂 Thumb 代码复现一个字节错误被上层忽略的分支；这是合成异常案例，不能推断本次相机出现了该故障。

## 固定来源

|---|---|
| 官方 X1D 1.25.0 FARM，1808280 字节 | `317841f6f4dff599cda8c83f2b4912f78534db20e7690d0b14b0cd5f1b8c39ca` |
| 同包 `power-control-v1.25.0-14703-9b140c9.bin`，48455 字节 | `dc0a77dd46f7e07a5640fb9407e077b8f544871d007f9c3fa4233ea5fc8e7616` |

第二项由官方 rootfs 的 `./lib/firmware/hbl/power-control/` 直接在电脑内存中读取。以下 SPC 地址使用其向量表对应的 `0x08000000` 基址，不是 SUC 地址；没有核验实机 SPC Flash 全量内容。

## FARM 的缓存早于发送结果

完整 IMX161 应用函数 `0x2305d0` 先构造曝光和其他参数，然后执行：

1. `0x23081c` 将配置的 `0xd0` 字节复制到 `0x6db3e8`。
2. `0x23082c–0x230884` 比较新缓冲 `0x6db2e8` 与缓存 `0x2b214c`，确定本次传输长度。
3. `0x2308b0` 把完整 256 字节新缓冲复制到 `0x2b214c`。
4. `0x230958` 才调用 `0x234c64` 发送 SPI 请求，并返回其结果。

因此 `0x2b214c` 不能命名为“已成功应用参数”。即使请求稍后失败，软件缓存也已更新。曝光、增益和 SVR 的独立更新函数 `0x22f2a8`、`0x22f350`、`0x22f41c` 同样在发送前复制缓存。

`0x234c64` 构造来源 FARM 1、目的 SPC 2 的 `0x23` 请求，在 `0x234d34` 经 `0x1e8718` 等待 `0x24` 回复，之后检查回复状态。请求发送、回复成功、传感器锁存是不同的证据层级。

## SPC 的回复路径

原消息分发在 `0x08004f36` 识别 `0x23`，在 `0x08004f5e` 调用 `Spi_Tx`（`0x080065c0`）。函数返回后，`0x08004f62–0x08004f82` 构造 `0x24` 回复：返回零转为状态零，非零统一转为状态一。

`Spi_Tx` 的正常路径先检查软件初始化与使能、地址和长度，再选择传感器、发送芯片编号与地址、逐字节发送内容。跨地址 `0x80` 时重新建立一段传输。尾部 `0x0800665c–0x0800666a` 有界等待 SPI 状态掩码 `0x80` 清零，然后撤片选、清控制位 `0x40`，最后返回。

问题在于逐字节辅助函数 `0x080064f8` 可以返回一，但外层在 `0x08006614`、`0x0800661a`、`0x08006640` 调用后未检查该值。辅助函数内部等待接收状态超时会先撤片选；外层仍可能继续处理余下字节，最终返回零。不能只看尾部有等待就断言每个字节必然完成。

固件里的 `Sensor_Start`（`0x08006328`）对应供电与初始化顺序，末尾还调用强制待机操作；该函数名也不能当作本次照片开始积分的证据。

## 原 Thumb 代码的合成复现

[离线模型](research/spc_spi_reply_model.py) 核对完整 SPC 哈希，执行原消息回复片段、完整 `Spi_Tx`、逐字节函数、状态读取、控制位修改和 GPIO 写函数。没有用替身替换这些原函数。ROM 只读且可执行，合成 RAM 和外设页不可执行；执行范围、写入范围和总指令数均受限。外设状态值由模型明确给定，不连接相机。

| 合成案例 | 原代码结果 |
|---|---|
| 地址 2、5 个数据字节，状态始终就绪 | 状态零；7 次字节调用均返回零，最终撤片选并关闭 SPI |
| 地址 `0x7f`、3 个数据字节 | 在 `0x80` 重新选择并发送地址，字节序列正确 |
| 初次就绪检查超时 | 状态一；没有数据寄存器写入 |
| 首个发送字节的接收等待超时 | 该辅助调用返回一并撤片选，外层继续，最终仍回复零 |
| 第一个数据字节的接收等待超时 | 同样回复零，后续数据寄存器写入发生在撤片选之后 |
| 最终状态 `0x80` 不清零 | 回复一；该返回分支仍保留片选和 SPI 控制使能 |

六例均实际通过断言；四个超时案例均执行了原代码的 4097 次状态读取，没有缩短原循环。截断或错误固件被拒绝。完整状态流摘要、字节序列、片选变化、源码哈希与执行计数见 [spc-spi-reply-validation.json](build/spc-spi-reply-validation.json)。

这些结果只限定“成功回包”的解释范围，没有发现新的积分事件，也不要求修改原厂 SPC。下一步仍需传感器同步与曝光编码生效帧的对应证据；不能用这个回复替代物理积分边沿。
