# 原厂通知时序观察器

记录日期：2026-09-10，北京时间。

用户反馈机械快门约 1/16 秒、界面额外延迟为零时，先听到快门动作，再见闪光，照片未接到闪光。这是用户观察，尚未测量镜间快门遮光、传感器感光窗口或实际射频时刻。用户要求分两组采样，并亲自说明各组使用机械还是电子快门。

## 本轮状态

独立观察器已编译、临时上传并在相机内启动，四个 Qt 回调在机内通过纯内存检查。用户已经自行拍摄两张，明确标记第一张为电子快门、第二张为机械快门。两张均收到完整四条原厂通知；记录结束后已正常停止观察器并移除自有临时服务，结束标记为 `stopped`，总样本数为 9（启动就绪一条、两张各四条）。

本轮连接后，原引闪常驻服务查询结果为 `unknown`，原厂 GUI 为 `active`，旧临时目录不存在。此前引闪版本的成功安装属于历史结果；当前并未重装引闪程序或改变 GUI。

观察器只订阅原厂已有 DBus 信号，不构造相机控制代理、不调用相机控制方法，也没有无线发送入口。试拍、切换快门类型均由用户操作。只把记录器相对启动时刻的微秒数和事件类型保存到自有临时文件，不保存通知携带的曝光值、设备标识或照片内容。

## 两类开始事件

来源固定为官方第一代 X1D 1.25.0。

| 记录名称 | 来源 | 已建立的含义 |
|---|---|---|
| `sequence_start` | SUC 的 `cambody_exposure_seq_started_event`，Linux 原厂 DBus 信号 `exposure_seq_started(int)` | 拍摄流程开始的软件通知；不等同于传感器已经开始感光 |
| `farm_start` | 原厂 `SensorExposureStart` | 既有引闪版本使用的开始通知 |
| `farm_done` | 原厂 `SensorExposureDone` | 用于核对与同次采集有关的后续通知 |
| `farm_ready` | 原厂 `ReadyForExposure` | 用于核对流程间隔和就绪状态 |

同版 SUC 固件为 `camera-control-v1.25.0-14903-666e0d4.bin`，SHA-256 为 `6bce5b264f431250be952dcfcaefee45a435a6355ebc22b45c9e824c165725a7`。SUC 拍摄函数 `0x08005250` 在 `0x08005286` 调用 `0x0800eeb4`，发送 `0x259` 事件；后续才进入准备、flush 等步骤。机械分支会向 FARM 发 `0x2a` 或 `0x21d`，对应 `handle_flush`。该 FARM 路径在 `0x1c5240` 提交传感器控制后，于 `0x1c52a0` 调用开始通知包装。

同版 `libappscommon.so.1.0.0` 的 SHA-256 为 `2d834be366ba5a78cf370e679f28a5bb171b8dc5944fe2f69e81c2a170ddc263`。`CamBodyProxy::connectExposureSeqStarted()` 使用 `exposure_seq_started` DBus 信号，再转成 Qt 的 `exposureSeqStarted(int)`；观察器直接使用前者，并丢弃整数值。

这证明的是软件生产步骤及合法被动订阅入口，不能单凭静态调用顺序保证 Linux 的实际到达先后。此次观察器用同一个进程、同一单调时钟记录各通知，正是为了核对实际到达差；它仍不能测量无线发射、闪光发光或物理曝光窗口。

## 运行约束与恢复

- 程序和记录位于 `/tmp/hbl-wireless-flash/observer`，独立服务文件位于 `/run/systemd/system/hbl-event-observer.service`。
- 最长记录五分钟，最多 512 条；达到任一限制会自行退出。原厂通知服务更换、DBus 断开、时钟或写入失败也会退出，无自动重启。
- 用独占锁防止重复实例，目录权限为 0700、记录为 0600；拒绝覆盖已有记录。
- `observer-stop.sh` 只停止和移除本轮观察器服务，保留记录，不触碰原厂或引闪服务。关机后临时文件失效。
- 本观察器没有接通菜单中另外三个 FARM 阶段；这些阶段的装载缺口仍见 [另外三个起点核对](PHASE_EVENT_RESEARCH.md)。

## 构建和机内验证

独立执行 `build_event_observer.py`，输出在 `build/event-observer-build`，不会重建或覆盖原引闪包。

当前已运行观察器 SHA-256：`e4a0c1c8947173c4467d6f33f5fdf55e2c30ac554de674263ab97107876a63a6`。

使用同版 Qt 5.5.1 与原厂库；动态重定位区保持旧加载器需要的连续布局。两个较早构建在文件检查阶段退出，没有开始采样。原因已定位到当前 Zig 的 `lstat/fstat` 兼容包装使用通用结构版本 0，而同版 ARM glibc 2.22 的转换函数 `0x4a2f7a4c` 只接受用户态版本 3。当前程序显式调用正常 `__lxstat/__fxstat` 的版本 3，并静态核对结构中的模式与所有者偏移；机内已通过目录、锁、记录文件和 DBus 订阅启动检查。

## 两次用户试拍的结果

下面以每张 `sequence_start` 在观察器中的到达时刻为零，单位为毫秒。用户只为本次两张明确标注了快门类型，未为这两个样本分别提供曝光时长；不能把更早对话中的快门速度自动套入。

| 观察器收到的通知 | 第一张：电子快门 | 第二张：机械快门 |
|---|---:|---:|
| 拍摄流程开始 `sequence_start` | 0 | 0 |
| 原曝光开始 `farm_start` | 550.916 | 202.866 |
| 原曝光结束 `farm_done` | 1460.861 | 1085.328 |
| 原曝光就绪 `farm_ready` | 1468.887 | 1093.475 |

这两张中，新候选开始通知分别比原引闪入口早到约 **551 ms、203 ms**。这是同一记录进程和单调时钟上的通知到达差，已经超出单纯静态调用顺序的推断；但每种模式只有一张，不能据此给出抖动范围、可靠性概率、固定引闪延迟或物理曝光窗口。

原曝光开始到结束通知的间隔分别为 909.945 ms 和 882.462 ms；这些间隔不能直接解释为照片设置的曝光时间。两种模式之间的差异也可能受本次拍摄准备、对焦状态、设置及消息调度影响，当前样本不足以分离这些因素。

详细脱敏记录保存在 [两组 JSON](build/event-observer-build/two-shutter-groups.json)，安装和正常停止的回包保存在同目录 `installation.json`。本轮没有接入新的自动引闪起点，没有实际引闪时刻的测量；原三处 FARM 阶段仍保持未接通状态。
