# 四份压缩 JPG 的内存预算

用户要求的 Latest、Current、Previous、Next 都是**完整压缩 JPG 文件数据**。四张不同照片的缓存费用是它们实际分配容量之和；相同身份只保存一份，角色增加不增加压缩数据。解码与 GPU 是另外的显示费用，不能把全图 RGB32 大小当作 JPG 文件大小。

## 数量与字节上限同时约束

离线候选先采用以下可调额度，以检验准入和退化逻辑。这是工程初值，不是实机余量证明。

| 预留类别 | 分类上限 | 计费内容 |
| --- | ---: | --- |
| 完整 JPG 缓存 | 64 MiB，最多四个身份 | 原数组 capacity、头部和拥有引用开销；包含旧读取者未释放的缓存 |
| 读取/传输在途 | 32 MiB，最多一个后台任务 | 读卡输入、IPC 发送/接收副本、拼接和扩容时同时存活的旧新块 |
| 屏幕显示资源 | 16 MiB | 实际 CPU 像素容量、正在显示和退休 GPU 纹理的预留 |
| 解码工作区 | 8 MiB 候选预留 | codec 临时分配；实际最大值尚未验证 |
| 新增托管总量 | **96 MiB** | 以上所有预留合计同时受限，分类上限不能同时占满 |

每次开始分配前同时取得分类和总额度；失败先撤销邻图预取。计费随最后一个拥有引用释放，退出界面或取消请求不能提前扣除仍活着的数据。原数组变为最终缓存且没有复制时，仅转移费用类别；发生复制就必须另留额度。`byte_budget.h` 已验证这个合同，真实数组、Qt/codec 隐式分配和 GPU 驱动尚未接入计费。96 MiB 因而不是已实现的整机实际 RSS/显存硬上限。

示例只是假设文件大小，不来自用户照片：四份 JPG 每份 12 MiB，共 48 MiB；加一份 12 MiB 在途数据、16 MiB 显示额度和 8 MiB 工作区，预留合计 84 MiB，可以通过该模型。四份每份 16 MiB 共 64 MiB，再加同样的 16 MiB 在途、16 MiB 显示和 8 MiB 工作区，合计 104 MiB，必须减掉邻图或等旧任务释放，不能因“只有四张”继续分配。只常驻、不解码传输时是 64 MiB 压缩缓存，加实际显示资源。

## 显示阶段另计

以已有静态尺寸 8176×6128、RGB32 紧密排列估算：单张全解码是 200,410,112 字节，即 191.126 MiB；DCT 1/8 预览 1022×766 是 3,131,408 字节，即 2.986 MiB。实际 stride、纹理格式、对齐和驱动保留还可能增加。可以从缓存中的完整 JPG 按需解码屏幕预览，不要求先把四张全部解码。

邻图后台工作首先完成完整 JPG 读取，不必提前解码。解码并发为一个；预览就绪前再检查请求代次，过期输出不上传。当前显示纹理与正在释放的旧纹理都计费，旧纹理未释放时不能无限继续上传。拍摄开始立即取消邻图排队和后续解码准入；已运行的不可中断库调用只能完成后丢弃，不能声称能同步杀掉它。

现有 Full 路径在上传瞬间可能同时存在一份 CPU 全图和一份 GPU 全图，合计约 382.252 MiB。若再保有 64 MiB 压缩缓存和 8 MiB 工作区，已达 454.252 MiB，尚未包含其他 GUI 资源、系统、驱动和原厂拍摄编码写卡峰值。Main 转达的旧实机 MemTotal 为 511,832 KiB，即 499.836 MiB，它是全系统可见总量，不是当前可用内存；上述组合仅留下约 45.584 MiB，不能据此批准 Full。

因此 96 MiB 初始托管预算下，现有 CPU/GPU 双全图方式不能获得 Full 准入。后续需要实测后另定上限，或实现当前图的分块/区域显示，才能在该内存版声明可用 Full；目前两项均未完成。原读取端既有 Full 包保持冻结，本方案不把它偷偷算进“96 MiB 足够”的结论。

## 退化顺序与生产优先

1. 先取消尚未开始的两侧预取；有明确翻页方向时优先撤掉相反侧。目录边界缺少某一侧时无需创建空任务。
2. 回收没有解码/GPU 引用的邻图完整 JPG。最多保留一个后台读/传任务、一个解码任务；两侧可以排队，但不能并行复制两份大 JPEG。
3. 当前 JPG 已缓存就继续使用，保留最新拍摄角色。若 Latest 与 Current 同身份，仍是一份数据；两侧缺失不自动改变用户当前图。
4. 当前图准入失败时暂停预取，用已约定的读取/原厂回退边界处理；不能把读失败、损坏或错配 JPEG 当成“确认无 JPEG”而新增 RAW 读取。退出释放三个浏览角色，最后旧引用结束后实际回收，保留 Latest。
5. 最新 JPEG 超过剩余总额度、借用型输入、取锁失败或无法取得可靠身份时，本轮缓存不发布，原 writeFile 返回和 freeBuffer 路径照常推进。必要时临时只有最新/当前两角色，甚至跳过本轮新增缓存；不能为了满足四角色常驻阻塞生产。

原厂拍摄、编码、写卡及系统峰值尚无本轮测量。它们应先从真实可用余量中保留，再决定本功能是否允许启用上述 96 MiB 初值。本任务未读取设备或用户照片，不能宣布实机内存足够、速度变快或卡顿已解决。
