# 持久化与升级、降级后的行为

用户于 2026-09-14 明确的设计目标：补丁在当前支持版本可用；升级到未支持版本后，仅保存在相机内而不启用；以后通过原厂固件降回支持版本，补丁自动恢复，中间无需重新安装补丁。这不是要求旧补丁直接支持任意新固件。本次讨论为可行性分析，不表示已经实现或授权执行固件更新。

## 已有静态依据

来源仅为本地官方 X1D-50c 1.25.0 解包基线：

- `lib/systemd/system/media-data.mount` 定义独立的 eMMC 第五分区挂载为 `/media/data`，说明其用于持久数据。
- `hbl-upgrade` 在两组 boot/root 分区中选择非当前组，格式化所选分区并展开新 rootfs；普通系统目录里的定制启动项不能假定随新系统迁移。
- `usr/bin/hbl-post-upgrade` 清理 `/media/data/upgrade` 暂存目录。因此该目录不适合留存补丁；尚未核验未来升级脚本、恢复出厂或全部配置迁移逻辑会否清理其他目录。
- 当前补丁依赖 GUI、消息服务和 FARM 的实际代码及摘要；单看显示的固件版本号不足以证明所有组件已经回到兼容状态。

## 需要同时解决的三层

1. **留存层**：独立目录保存补丁包、版本清单和用户设置；核对升级、降级以及失败恢复时的保留范围。
2. **启动层**：新系统或降级后的原厂系统必须能够重新到达补丁加载器。仅在当前 rootfs 增加 systemd 服务不能证明这一点；目前未确认跨更新保留的合适入口，也未修改启动环境或升级程序。
3. **兼容层**：按实际组件摘要及代码前检选择已验证补丁；未支持或组件混合状态下不加载。回到全部匹配的版本后，才自动装入相应 RAM 补丁。

## 验收边界

普通重启自动加载和“升级后停用、降级后自动恢复”是不同的验收用例。后者还需要覆盖文件留存、启动入口、设置保留、组件版本识别及异常升级后的行为。仅完成开机服务不应宣称跨固件更新持久化完成。目前四模块仍在临时 RAM 装载验证阶段。

## 2026-09-14 离线验证结果

用户要求开始验证后，运行 `verify_persistence.py`，核对固定官方 CIM 整包 SHA-256，在内存中扫描 rootfs 全部 3873 个归档条目及选定路径下 314 份文本文件，保留启动链接元数据并解析相对链接。没有执行固件或连接相机；完整证据为 `CodeTests/persistence-audit.json`。

- 所有归档符号/硬链接中未发现解析后指向 `/media/data` 的链接。选定脚本、配置和启动 unit 的直接数据区引用涉及挂载、配置数据库、日志、更新暂存等；未发现通用的持久数据区补丁自启入口。这是有界静态检索结果，不证明所有原生二进制中的间接调用均不存在。
- `media-data.mount` 明确 `After=victory-gui.service`。此前已验收并卸载的空按钮方案将加载器和启动 drop-in 都放在 rootfs，解决了普通重启自启，但没有解决跨系统更新保留。
- 按 1.25.0 升级脚本的目标分区选择及重建规则，文件模型的四项检查通过：初始有自启项；升级后数据可在模型中保留但新系统无自启项；旧分区暂时还有自启项；再正常降级会重建旧分区，从而两组系统都失去定制入口。**原厂重新安装旧版本，不等于直接切回完整保存的旧系统。** 数据保留在该模型中是明确前提，不是实机升级保留的测量结果；未知版本脚本不在模型验证范围内。
- 固定包内 U-Boot 默认启动走系统 boot/root 分区，`preboot` 为空；该版升级脚本不刷 U-Boot，但会改部分引导环境。仅凭“不刷 U-Boot”不能证明存在已经可用、安全且跨所有更新保留的补丁加载入口；未读取或修改实机引导环境。
- 原厂 `erase_configstore.sh` 的直接数据区删除针对 Favorites 和配置数据库；这不足以给未来升级或恢复出厂的整个数据区保留作保证。

**当前结论：现有 rootfs 开机自启方案不满足用户要求。** 实现该要求还需要独立于被重建系统分区的加载链，以及经过验证的版本选择和失败回到原厂路径。尚无可交付的跨升级/降级自动恢复实现，不应靠把启动项复制进两个系统分区或仅存入数据区来宣称完成。本次相机持久存储、引导器和更新流程均未改动。
